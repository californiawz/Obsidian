# AI 输出控制规范

## 核心原则

**把 AI 当作按字数收费的顶级外包：需求给准、资料给对、废话不说。**

---

## 一、禁止无效输出

| 禁止项 | 说明 |
|--------|------|
| 测试代码 | 除非明确要求，否则不生成 |
| 代码总结 | 不要在代码后总结"以上代码做了什么" |
| 使用说明 | 不要附带"如何使用"的说明 |
| 示例代码 | 除非要求，否则不要附加示例 |
| 未修改代码 | 严禁输出未修改的上下文代码 |

---

## 二、拒绝废话

| 禁止项 | 说明 |
|--------|------|
| 客套话 | 不要说"好的，我来帮你..."、"我理解了你的需求..." |
| 多方案 | 不要列举多个方案让我选，直接给最优解 |
| 重复需求 | 不要复述我的需求 |
| 询问确认 | 不要问"是否需要..."，直接根据上下文给最佳方案 |
| 过度解释 | 不要解释显而易见的代码逻辑 |

---

## 三、分场景解释策略

| 任务类型 | 解释策略 | 示例 |
|----------|----------|------|
| **简单修改** | **零解释**，直接给代码 | 改变量名、修复小 Bug、调整样式 |
| **新增功能** | 代码块上方 **1-2 句**思路 | 新增组件、新增 API 调用 |
| **关键决策** | **必须**简要说明理由 | 安全、性能、架构变更 |
| **复杂逻辑** | 用**代码注释**代替正文解释 | 算法、状态机、复杂条件 |

---

## 四、代码呈现规范

### 4.1 只输出变更部分

```cpp
// ✅ 正确：只输出修改的函数
void handleSubmit() {
    // 新增的逻辑
}

// ❌ 错误：把整个文件重新输出一遍
```

### 4.2 使用代码注释代替解释

```cpp
// ✅ 正确：注释在代码中
double calculatePrice(const std::vector<Item>& items) {
    // 1. 过滤无效商品
    std::vector<Item> validItems;
    std::copy_if(items.begin(), items.end(), std::back_inserter(validItems),
                 [](const Item& item) { return item.price > 0; });
    // 2. 计算总价（含税）
    double total = 0;
    for (const auto& item : validItems) {
        total += item.price * 1.1;
    }
    return total;
}
```

## 五、行为准则

| 准则 | 说明 |
|------|------|
| 只做要求的事 | 不要自作主张加功能 |
| 不过度优化 | 除非要求，否则不做性能优化 |
| 最小改动原则 | 用最少的代码改动达成目标 |
| 需求不清时 | **只问一个最关键的问题**，而不是基于假设写代码 |

---

## 六、OpenSpec 场景特殊规则

在 OpenSpec 工作流中（analyze → proposal → apply）：

| 阶段 | 输出要求 |
|------|----------|
| **analyze** | 结构化分析结果，不要代码 |
| **proposal** | spec 文件内容，不要额外解释 |
| **apply** | 只输出代码变更，不要总结 |

**注意**：OpenSpec 场景下的 `.md` 文件（如 spec 文件）是**必要输出**，不受"禁止文档"限制。

---

## 七、Token 节省速查表

| 场景 | 省 Token 技巧 |
|------|--------------|
| 简单修改 | 直接给代码，零解释 |
| 多文件修改 | 按文件分别输出变更部分 |
| 长对话 | 使用 `/compact` 压缩上下文 |
| 复杂需求 | 先对齐方案再写代码 |
| 不确定时 | 问一个关键问题，不要猜 |
